# Client-side tempo detection and a Click Track that is not a Stem

A Source Mix needs a Tempo Detector and a Beat-synchronized Click Track, but the app is fully client-side (ADR 0001) and every heavy pass already runs in a Web Worker on `Float32Array` buffers. We adopted `@audio/beat` (pure-JS Ellis-DP + comb-filter tracker, MIT, consumes those buffers directly at ~450× real-time) over `realtime-bpm-analyzer` (stream/DJ-oriented API shape), a hand-rolled tracker on our own `stft`/`fftRadix2` (re-implementing code that ships tested and benchmarked), and desktop-only Essentia/librosa (rejected outright; kept only as the verification anchor `scripts/check_bpm.py`). Separately, the **Click Track is deliberately NOT a Stem**: the four `StemName` identities are woven through session storage, Export Bundle packaging, and Custom Mixdown presets, and a fake fifth stem identity would contaminate all of them — the Click Track is a parallel concept that merely offers mute/volume like a Stem, exports only as its own separate file, and is never summed into any mixdown preset.

Considered options: `@audio/beat` vs `realtime-bpm-analyzer` vs DIY tracker vs Essentia/TempoCNN vs server API (breaks ADR 0001); Click Track as fifth Stem vs separate concept.

Detection runs exactly once on the Source Mix at decode time; re-detection on the Drums Stem after separation was rejected because an empirical pass on `audioslave_stone.mp3` showed the two agree (107.7 BPM, 503 vs 513 beats) while adding a second code path.

The honesty rule above is pinned to a number so it can be quoted, not re-invented: the Click Track rail reads a tempo as certain only for a **lone candidate at confidence ≥ 0.99** (`isConfidentReading` in `StemPlayer.tsx`, whose label then says "solid reading"); every other outcome — multiple candidates, or a lone one under the bar — presents the ranked BPM candidates and makes the user pick the feel they hear. The bar sits deliberately near 1 because a confident-but-single Ellis-DP reading on a clean 4/4 rock track is the only case where presenting alternatives would be noise; everywhere else octave ambiguity is real and stays a user decision.

The follow-up decisions on automatic Downbeat reading and Beat Grid drift repair are recorded in [ADR-0011](./0011-downbeat-reading-and-beat-grid-repair.md), which extends this ranking-over-certainty philosophy to the phase axis.

## Addendum — the heard-alignment seam for the Click Track (2026-11-02)

The Click Track lane's relay anchor is asserted at the **headless engine seam**: every mid-playback lane edit (enable, Meter, Downbeat hunt, Beat Grid re-lock) relays from the live playhead via `reanchorClickOnLivePlayhead` in `src/lib/stemPlayerEngine.ts`, pinned by tests reading the mock `AudioContext`'s recorded `source.start(when, offset)` arguments — the same timeline `play()`, `seek()` and `setTempo` already anchored on. The _heard_ Click-vs-Stems alignment through the WSOLA AudioWorklet pipeline is out of scope for that headless contract: no mock models worklet output latency. A future regression there is measured at the **export seam** — the exported Click Track file decoded with `decodeWavOnsets` against the Beat Grid — not asserted against a browser session.

## Amendment — Drums Stem re-detection adopted (2026-11-02)

The rejection above kept the wrong axis. Its anchor ("107.7 BPM, 503 vs 513 beats") compared the two channels at _tempo_ level only; what breaks for a listener is grid _position_: on the reference Source Mix the tail (210–294 s) carries 54/170 clicks >80 ms from any librosa strong-onset truth, and the RAW tracker grid shows identical stats — the defect lives in what the tracker was FED, not in repair (ADR-0011 Amendment, whose closing line points exactly here: "Any fix there is a new Beat Grid detection seam (detect on the Drums Stem)"). The "second code path" objection is stale too: the worker pass already consumes any `Float32Array` channel — the re-lock hint (ticket 06) reused the same machinery — so the policy point is only which channel feeds the single pass.

Adopted: on Separation completion the Tempo Detector re-runs over the Drums Stem's channel-averaged samples, abandoning any Source Mix pass still in flight (ticket 06's one-pass-at-a-time rule); with no usable Drums samples the decode-time Source Mix reading stays untouched, and a failing stem pass keeps the existing reading (fallback, never a gap). Re-lock and Session-recovery passes follow the same channel policy. Honest boundary: the stem-channel tail A/B could NOT be re-measured on this machine (no isolated stems on disk; separation is client-side), so what ships grounded here is the channel-level attribution of the tail defect — the grid-quality A/B lands on the user's own material in the app. Recorded on ticket 07; the guaranteed manual escape hatch when both channels miss is ticket 08 (four-tap Click calibration), deferred behind an OpenDesign run.

## Amendment — hand-calibration escape hatch adopted: Calibrate the Click (2026-11-02)

Both automatic channels can miss the same groove, and at that point the honest options are "here are my ranked readings" (wrong) or silence. Adopted instead: a guaranteed manual route. The user taps four beats on the Mix Tab spine (the `BeatGridTapCalibration` strip); derivation is pure arithmetic at the engine seam, `calibrateClickGrid` in `src/lib/stemPlayerEngine.ts` — pulse is the median of the sorted inter-tap deltas, the grid anchor is the first tap, and fewer than three taps or any gap under 0.25 s (240 BPM) or over 2.5 s (24 BPM) is refused with a named reason, never folded into a half-calibration. Confirm re-locks through the exact ticket-06 machinery (one heavy pass, hint = derived BPM), then `reanchorBeatGridToAnchor` slides the Beat Grid as one rigid body by the smallest shift mod pulse that lands a beat on the tap lattice — the Detector's beat positions stay (they follow the drums), only the anchor moves, and no grid is ever re-derived from the BPM number alone.

Honesty pins: the rail appends "· calibrated by hand" to the BPM line and its confidence line names the taps ("your N taps anchor the grid") — it never dresses a by-hand decision up as a Detector reading; any later automatic pass supersedes and clears the claim. The reading persists with the Session as its own `SessionClickCalibration` field (sibling to `tempo`, gate-validated on load like the Click Track settings), so Session Recovery resumes the by-hand claim. Recorded on ticket 08; the tap-strip view is agent-authored there because the OpenDesign MCP was dead that session (documented fallback).
