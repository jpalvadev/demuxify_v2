# Solo and Mute are per-Stem exclusive

A Stem's rail carries two expressive controls, Mute (M) and Solo (S). Left free to combine, the state `solo && muted` is a dead end: the gain matrix silences everything the moment a soloed Stem is muted (solo still claims isolation, mute still claims silence), the Stem is neither a solo nor the band, and no UI control ever asks for that pair. Yet the engine's mixer state was representable, so every seam had to trust that no caller would build one — and the **Session** restore path was exactly that kind of caller: an old stored mixer could carry the pair straight back into a resumed **Stem** strip.

Adopted: **exclusive per Stem, last press wins**. Pressing Solo on a muted Stem clears its mute and plays it alone; pressing Mute on a soloed Stem drops the solo and silences that Stem, and the other Stems resume because isolation falls away with the solo. A second press of either control re-arms that axis. This is enforced at the engine seam in `src/lib/stemPlayerEngine.ts`: a press-on of either flag in `setStemSolo`/`setStemMute` clears the other, and constructor init runs the same clear over any `initialMixerStates` — no path (init, mid-playback edit, restore) can smuggle the pair. `applyGainMatrix` is untouched: its branch that silenced the whole matrix for a solo-and-muted Stem simply never fires anymore, while the live half of the matrix (solo isolates the unselected Stems, mute silences exactly one) keeps its behavior byte-for-byte. The press sequence is asserted on gain outcomes at the shared mock AudioContext factory, the same seam the existing mixer-state observicals use.

The **load rule differs from the runtime rule** for an honest reason: a restored Session has no press order to replay, so "last" is undefined there. `loadActiveSession` in `src/lib/sessionStore.ts` runs a mixer sanitizer at the same validation gate the existing Session Recovery tests already drive: a persisted Stem entry carrying both flags resolves to solo with the mute flag dropped silently — solo is the intent-revealing state, and a soloed-then-muted Stem is exactly what a user pressing S-then-M meant to be alone. The write side needs no rule: once the engine cannot produce the pair, nothing saved from a live session can gain it, so only legacy records pass through the sanitizer at all.

Why this answer is here: a future reader wondering "why does M clear S" (or the reverse) finds the pair was never a product state — it was an unenforced hole in the state space, closed at the seam that restore paths also cross.

Considered options: UI-only guard (rejected — restore paths smuggle the illegal pair back around any UI rule, as the grilling Q4/Q9 settled) vs engine-seam enforcement + load sanitizer (picked) vs dropping the Mute axis from Stems like the Click Track's died (rejected — the lane's mute was an affordance duplicated by switch-off + volume-0; a Stem's Mute has no duplicate and stays live, AGENTS.md sibling-trap note).

Sanitizer direction: solo-wins at load vs mute-wins — solo-wins picked; a muted-solo restore would silence the whole band, an outcome no press order produces under the runtime rule, while solo-wins is the one state both press orders can end in.

This is not about the **Click Track** lane: it has no Solo axis, and its mute concept died end to end in [ADR-0010](./0010-client-side-tempo-detection-and-click-track.md) (Amendment, Mix Rail Tidy-Up ticket 03), so it cannot carry the pair at all. Follows the retired-affordance discipline of [ADR-0011](./0011-downbeat-reading-and-beat-grid-repair.md) amendments: the pair stays pinned unrepresentable by the engine observicals and the `check:retired-affordances` gate extension (ticket 05).
